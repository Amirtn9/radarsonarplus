# Sonar Radar Pro 6.5.3 — گزارش اصلاحات ممیزی (Release Candidate)

تاریخ: ۲۰ اکتبر ۲۰۲۶

## تضمین‌ها و محدودیت‌های فنی

- **تغییر نکرده‌اند:** `ws_client.py`، `tunnel_logic.py`، `ssh_support.py`، `agent_runtime.lock.json`، `pro_scoring.py`، `access_policy.py` و `keyboard.py` نسبت به ۶.۵.۲ (مقایسه SHA-256). قرارداد پروتکل Agent همچنان `AGENT_PROTOCOL = 2` است.
- **تغییر محدود داشته‌اند:** `monitor_agent.py` صرفاً در انتخاب پورت/تست سلامت کانفیگ و `core.py` صرفاً در retry فرمان‌های WSS؛ منطق بالانسر یا قوانین مسیریابی تغییر نکرده است.
- اعلان‌ها دارای **at-least-once delivery** هستند؛ در قطع فرایند دقیقاً پس از پذیرش پیام توسط تلگرام و پیش از ثبت receipt ممکن است یک رویداد دوبار برسد. برای ردگیری، شناسه رویداد در متن درج می‌شود.
- رویداد پس از ۸ تلاش ناموفق به وضعیت `dead` می‌رود و تا ۹۰ روز برای عیب‌یابی حفظ می‌شود؛ از دست رفتن خاموش رخ نمی‌دهد، اما فرایند بازیابی دستی رویدادهای dead هنوز در UI وجود ندارد.
- برای کاهش بار پردازش، اندازهٔ گردش کاربران در هر ۳۰ دقیقه **۱۰ کاربر** است (`SONAR_PROBE_OWNER_BATCH`، سقف ۱۰۰). برای ۱۵۰ کاربر با مقدار ۱۰، هر کاربر حدوداً هر ۷.۵ ساعت نوبت می‌گیرد، به شرط تکمیل به‌موقع نوبت‌ها. تغییر مقدار باید پس از اندازه‌گیری بار واقعی انجام شود.
- DNS‌ تست SOCKS از طریق Xray انجام می‌شود؛ تشخیص سالم‌بودن قطعی کانفیگ هنوز به وضعیت مقصد آزمون و مسیر خروجی وابسته است. مقصد پیش‌فرض قبلی حفظ شده و می‌توان از `SONAR_AGENT_HEALTH_URLS` برای افزودن حداکثر چهار URL معتبرِ کنترل‌شده استفاده کرد.
- بررسی درستی SQL Trigger، migration و rollback در یک PostgreSQL واقعی انجام نشده است؛ صرفاً کنترل کد و آزمون‌های mock/آفلاین موفق بوده‌اند.

## هنوز کامل انجام نشده / نیازمند فاز جداگانه

1. **نصب Agent:** سلامت واقعی SSH، TLS، WSS، token، Xray، تست کانفیگ و rollback در Ubuntu VPS آزمایشی تأیید نشده؛ تضاد پورت ۸۰۸۰ نیز فقط روی سرور مقصد تشخیص قطعی دارد.
2. **تست انبوه کانفیگ:** صف پایدار با resume/checkpoint/cancel و کنترل مجموع ۶۰۰ کانفیگ هنوز پیاده نشده است؛ محدودسازی retry فقط یکی از خطرهای تکرار را کاهش می‌دهد.
3. **نظارت عملیاتی:** heartbeat مستقل Agent، پایش DNS/ICMP/TLS-expiry، SLA، status page، نرخ شبکه per-interface و disk I/O به‌صورت کامل اضافه نشده‌اند.
4. **Cron state:** شمارندهٔ قطعی سرور پایدار است ولی cooldown هشدار CPU، قفل‌های چندنسخه‌ای و همهٔ وضعیت‌های cron هنوز در حافظه باقی مانده‌اند.
5. **Conversation persistence:** سیاست `drop_pending_updates` در Bot از طریق `SONAR_DROP_PENDING_UPDATES` قابل تنظیم شده، ولی مقدار پیش‌فرض امن قبلی (=1) حفظ است. وضعیت Wizardها پس از restart به‌طور کامل پایدار نشده است.
6. **DB pool و فایروال:** آزمون بار واقعی، ظرفیت‌سنجی ۴۸ worker در برابر pool، بررسی NAT/IPv6، allowlist ابری و recovery firewall هنوز انجام نشده است.
7. **امنیت تست Xray:** مدیریت پورت‌های همزمان در یک Agent اصلاح شده، ولی رزرو سراسری پورت بین فرایندهای مستقل مستلزم آزمون و طراحی بیشتر است.

**بنابراین این بسته، نسخه RC با اصلاحات قابل‌توجه است؛ نه تأیید رفع صددرصد تمام ۲۰ مورد و نه نسخه Production Ready.**

## آزمون‌های اجراشده

- Python `compileall`: موفق.
- `bash -n` برای نصب‌کننده‌ها و اسکریپت‌های Bash: موفق.
- مجموعه کامل pytest: **۱۶۱ موفق، ۴ ناموفق، ۲ خطای آماده‌سازی، ۸ subtest موفق**.
- ۴ شکست و ۲ خطای آماده‌سازی از نبود `paramiko` و `python-telegram-bot` در محیط اجرای این نوبت هستند؛ نباید خرابی کد عملیاتی تعبیر شوند. مجموعه کامل با dependencies در CI پیش‌بینی شده اما در این محیط اجرا نشده است.
- ۱۳ آزمون اختصاصی جدید شامل گردش ۱۵۰ کاربر، گردش نودها، ساعت محلی، صف اعلان، افت ارتباط، رویدادهای سرویس، سنجش تصادم ۵۰ پورت و state machine قطع/بازیابی: موفق.
- نتیجه آزمون‌های mock جایگزین آزمون PostgreSQL/TLS واقعی نیست.

## راهنمای ارتقای امن

1. ابتدا snapshot و backup معتبر و قابل بازیابی از دیتابیس PostgreSQL و فایل‌های `secret.key`، `sonar_config.json`، known_hosts، فایل‌های TLS و Agent در مقصد تهیه کنید؛ هیچ‌یک از این داده‌ها نباید داخل ZIP اشتراکی قرار بگیرند.
2. نسخهٔ ۶.۵.۲ را نگه دارید؛ نسخهٔ ۶.۵.۳ را ابتدا روی **staging** با دیتابیس clone شده اجرا کنید.
3. استقرار staging را با `bash install.sh --check`، سپس دستور ارتقای پشتیبانی‌شده `sudo bash install.sh --update` و `sudo bash install.sh --doctor` کنترل کنید. مشخصات نصب‌کننده را قبل از اجرای `--update` بررسی کنید.
4. در PostgreSQL پس از startup بررسی کنید `pro_job_cursors`، `pro_notification_outbox`، `pro_server_monitor_state` و ستون `pro_preferences.timezone` موجود باشند و تابع `sonar_workspace_track` مطابق نسخه اصلاحی جایگزین شده باشد.
5. تست پذیرش: حذف/ویرایش یک سرور staging، ثبت ۱۵۰ حساب و ۱۳ نود ساختگی، تشخیص قطعی در ساعت سکوت و ارسال بعد از آن، ۵۰ تست پورت، یک WSS timeout، و اتصال آزمایشی Agent با گواهی و توکن واقعی.
6. پس از smoke موفق، Rollback واقعی داده و فایل روی staging را تمرین کنید؛ سپس برای canary روی یک نود مجزا تصمیم بگیرید. از `kill -9` یا حذف سرویس ناشناسی که پورت ۸۰۸۰ را اشغال کرده خودداری کنید.
7. نصب Agent جدید روی سرور ایران **جداگانه** باید از طریق مسیر امن موجود انجام شود. ارتقای ربات به تنهایی فایل Agent قبلی را خودکار جایگزین نمی‌کند.

## رگرسیون / سازگاری

پروژه پایه همچنان Telegram Bot، PostgreSQL، SSH با Host-key Verification و Agent WSS/TLS اختصاصی دارد. ساختار منوها، گزینه‌های اصلی، بالانسر و routing حفظ شده‌اند. برای مرجع‌برداری از پروژه‌های دیگر، هیچ بسته اجرایی یا معماری transport ناسازگار جایگزین نشده است.
