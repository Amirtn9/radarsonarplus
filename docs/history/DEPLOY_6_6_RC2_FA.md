# SONAR RADAR Pro 6.6.0-rc2 — راهنمای نصب آزمایشی و پذیرش Relay/Traffic

## ۱. پیش‌نیاز و پشتیبان

**روی سرور اصلی نصب مستقیم نکنید.** VPS آزمایشی با امکان بکاپ/restore و در صورت امکان کلون دیتابیس واقعی لازم است. از PostgreSQL، `/etc/sonar-bot.env`، `secret.key`، فایل‌های nginx و systemd و سورس موجود نسخهٔ ۶.۵.۴ کپی قابل بازیابی تهیه کنید. کلیدها را در فایل ZIP منتشر نکنید.

فایل ZIP را باز کنید و در همان دایرکتوری که `install.sh` وجود دارد اجرا کنید:

```bash
python3 scripts/verify_manifest.py
bash install.sh --check
sudo bash install.sh --doctor
```

بعد از تأیید restore آزمایشی، ارتقای محیط staging:

```bash
sudo bash install.sh --update
sudo bash install.sh --panel
```

از `--clean-install` استفاده نکنید. گزینهٔ ۰۴ برای HTTPS را بعد از بررسی دامنهٔ آزمایشی اجرا کنید؛ قبل از تنظیم nginx صدور گواهی را تأیید کنید.

## ۲. تست عملی SSH مسدود از خارج

1. یک سرور ایران **A** با Agent از قبل نصب‌شده، WSS/token معتبر و قابلیت `ssh_relay` فعال انتخاب کنید. Agent A باید بتواند به IP عمومی/پورت SSH سرور مقصد B دسترسی داشته باشد.
2. از پنل مدیر، Agent A را در استخر انتخاب/تأیید کنید. برای مدیر نیاز به تأیید جداگانهٔ مالک نیست؛ سایر کاربران این Agent را خودکار نمی‌بینند.
3. روی B، پورت SSH فقط از IP سرورهای ایران قابل‌دسترسی باشد؛ سپس از مرکزی مسیریابی را آزمایش کنید. انجام این تست را **فقط روی سرور آزمایشی خودتان** با دسترسی کنسول اضطراری انجام دهید.
4. افزودن B باید SSH مستقیم را اول امتحان کند و در خطای شبکه سراغ WSS Relay برود. احراز هویت و اثرانگشت SSH همچنان باید اعتبارسنجی شود.
5. با رمز نادرست/اثر انگشت تغییرکرده، اطمینان بگیرید سیستم اتصال را رد می‌کند و fallback این خطاها را مخفی نمی‌کند.
6. دسترسی Agent A به پورت SSH مقصد را مسدود کنید؛ انتظار می‌رود اتصال رد شود و خطا معادل «SSH unreachable»، نه خاموشی قطعی VPS، باشد. ICMP Check-Host فقط برای تشخیص جانبی است.

**نکته:** اگر هیچ Agent سالمی در سمت ایران ندارید و SSH مستقیم مرکزی مسدود است، برای نصب Agent اول باید مسیر شبکه مجاز دیگری مانند کنسول هاست یا سرور مجاز خودتان فراهم کنید؛ کد نمی‌تواند محدودیت شبکه را بدون مسیر موجود برطرف کند.

پورت‌های Relay پیش‌فرض `22,2022,2222` هستند. برای مقصد روی پورت دیگر، تنظیمات روی Agent تغییر کنند، اما بازکردن پورت نامحدود توصیه نمی‌شود.

## ۳. آزمون ترافیک Agent

- با مدیر اصلی وارد منوی «📊 ترافیک Agentها» یا صفحهٔ مدیریتی وب شوید.
- `get_stats` و heartbeat هر Agent را فعال/بررسی کنید؛ بعد چند تست کانفیگ یا اتصال SSH انجام دهید.
- مجموع از آخرین ریست، «امروز»، «۷ روز» و «۳۰ روز» و شناسهٔ مالک را بررسی کنید. زمان نمونهٔ آخر را حتماً ببینید.
- عملیات بازنشانی را تأیید کنید؛ دورهٔ جدید باید صفر/مقدارهای جدید را نشان دهد، دادهٔ تاریخچهٔ قبلی حذف نشود.
- بعد از restart Agent/ربات و وقفهٔ اتصال هم از عدم ثبت منفی و عدم شمارش مضاعف نمونهٔ تکراری مطمئن شوید.

API مدیر:

```text
GET  /api/fleet/traffic
POST /api/fleet/traffic/{agent_id}/reset   {"confirmed": true}
```

هر دو نیاز به احراز هویت نشست و سطح دسترسی مدیر اصلی دارند.

## ۴. پذیرش سناریوهای اصلی ۶.۶

- ثبت اشتراک سالم بدون Agent و نمایش تعداد کانفیگ‌ها، سپس افزودن Agent و انجام تست.
- نصب/ترمیم یک Agent موجود و نصب Agent دوم با پورت آزاد، تنظیم WSS/TLS/token و حفظ پورت/وضعیت قبلی در صورت شکست.
- توزیع تست میان چند Agent، صف/lease، پینگ/لود و جلوگیری از دوباره‌اجراشدن نامطمئن.
- تست یک کاربر عادی که به سرور/Traffic کاربر دیگر دسترسی نداشته باشد؛ دسترسی گسترده تنها برای مدیر اصلی.
- ورود وب با کد و reset، خروج از همه دستگاه‌ها، HTTPS، CSRF، محدودیت تلاش و سازگاری PostgreSQL.
- PDF فارسی با فونت وزیرمتن نصب‌شده، روی موبایل و دسکتاپ.
- هشدار زمان‌بندی‌شده، سکوت، قطعی و برگشت سرویس، افزایش ترافیک Agent.
- بازیابی کامل snapshot روی staging و بررسی اینکه دادهٔ قدیمی پاک نشده باشد.

## ۵. عیب‌یابی و بازگشت

```bash
sudo systemctl status sonar-bot sonar-web --no-pager
sudo journalctl -u sonar-bot -n 100 --no-pager
sudo journalctl -u sonar-web -n 100 --no-pager
sudo bash install.sh --doctor
```

اگر تست اشتباه/نصب شکست خورد، **فقط پس از توقف سرویس‌ها** از کد/تنظیمات قبلی و snapshot PostgreSQL پیش از ارتقا restore کنید؛ صرفاً بازگرداندن کد، rollback دیتابیس را تضمین نمی‌کند. از اشتراک فایل‌های لاگ حاوی IP، رمز یا token خودداری کنید.
