# SONAR Radar — نسخه ۴.۳

## 🔎 اول این را بخوان: یک سوال که باید جوابش را بدهی

علائمی که گفتی خیلی گویاست: **فقط وقتی نود ایران کار می‌کند، حتی `/start` هم جواب نمی‌دهد.**

`/start` در این پروژه هیچ کاری با نود ایران ندارد. مسیرش این است:
سه کوئری دیتابیس (همه در ترد جداگانه) → ساخت کیبورد → یک `sendMessage` به تلگرام.
هیچ SSH، هیچ وب‌سوکت، هیچ چیز سنگینی.

پس اگر `/start` هم می‌میرد، یعنی مشکل دیگر «صف و همزمانی در کد» نیست.
یعنی **خود پروسه‌ی ربات CPU گیرش نمی‌آید**. و شایع‌ترین دلیلش این است:

> **ربات و نود مانیتورینگ روی یک ماشین هستند.**

وقتی تست کانفیگ اجرا می‌شود، روی همان سرور چند نسخه‌ی `xray` بالا می‌آید و
`curl` مشغول دانلود ۱۰ مگابایتی است. روی یک VPS ایران با ۱ یا ۲ هسته،
CPU می‌رود ۱۰۰٪ و پروسه‌ی ربات (و Postgres) عملاً متوقف می‌شود.
از بیرون دقیقاً شبیه «ربات هنگ کرده» دیده می‌شود.

### چطور در ۳۰ ثانیه مطمئن شویم

```bash
# ۱) آیا نود مانیتورینگ همین ماشین است؟
sudo -u sonar_user psql -d sonar_ultra_pro -c \
  "SELECT name, ip, is_monitor_node FROM servers WHERE is_monitor_node=1;"
hostname -I
```
اگر آی‌پی نود مانیتورینگ همان آی‌پی این ماشین بود (یا `127.0.0.1`)، جواب پیدا شد.

```bash
# ۲) موقع اجرای «بررسی پینگ»، این را در یک ترمینال دیگر باز بگذار:
top -b -d 1 | head -20
```

```bash
# ۳) و همزمان لاگ ناظر جدید نسخه ۴.۳ را ببین:
tail -f /var/log/sonar/*.log | grep "EVENT LOOP LAG"
```

**خواندن نتیجه:**

| لاگ | CPU | معنی |
|---|---|---|
| `EVENT LOOP LAG` می‌آید | ۱۰۰٪ و پر از `xray`/`curl` | کل ماشین اشباع است → نود ایران را جدا کن |
| `EVENT LOOP LAG` می‌آید | CPU پایین | هنوز جایی کد سینکرون لوپ را بلاک می‌کند → لاگ را برایم بفرست |
| هیچ لاگی نمی‌آید | هرچه | لوپ سالم است، مشکل در شبکه/تلگرام است |

### راه‌حل واقعی اگر گزینه‌ی اول بود

نود مانیتورینگ را از ماشین ربات جدا کن. یک VPS ارزان ایران فقط برای ایجنت کافی است.
نسخه ۴.۳ تا حد زیادی درد را کم می‌کند (پایین‌تر توضیح داده‌ام)، ولی
اگر یک VPS تک‌هسته‌ای هم ربات را اجرا کند هم ده تا xray را، هیچ کد پایتونی نجاتش نمی‌دهد.

## تغییرات نسخه ۴.۳

### ۱. ناظر تاخیر event loop (ابزار تشخیصی) — `runtime.py`, `bot.py`

هر ثانیه یک `sleep(1)` می‌زند و اندازه می‌گیرد واقعاً چقدر طول کشید.
اگر تاخیر از ۱ ثانیه بیشتر شد، همراه با CPU و load average در لاگ می‌نویسد.
این دقیقاً همان چیزی است که بین «کد بلاک کرده» و «سرور اشباع شده» تفاوت می‌گذارد.

### ۲. باگ نشت شمارنده در استخر وب‌سوکت — `ws_client.py`

وقتی یک درخواست تایم‌اوت می‌خورد، کانکشن **دو بار** `_dispose` می‌شد:
یک بار در `except` و یک بار در `finally`. هر بار `_counts[key]` یکی کم می‌شد.

نتیجه: استخر فکر می‌کرد کانکشن کمتری باز است و **بیشتر از `max_per_key`**
کانکشن به ایجنت می‌زد. یعنی هرچه نود ایران کندتر می‌شد و تایم‌اوت‌ها بیشتر،
ربات کانکشن بیشتری به آن سرازیر می‌کرد. یک حلقه‌ی بازخورد تمام‌عیار.

اصلاح: در همه‌ی شاخه‌های `except` بعد از dispose، `conn = None` می‌شود.

### ۳. ایجنت دیگر کل ماشین را نمی‌بلعد — `monitor_agent.py`, `core.py`

- `xray` و `curl` با `nice -n 15` و `ionice -c 3` اجرا می‌شوند؛ یعنی «فقط وقتی CPU بیکار است».
- سرویس systemd ایجنت: `Nice=15`, `IOSchedulingClass=idle`, `CPUWeight=20`, `CPUQuota=60%`
- همه‌ی `subprocess.run` ها حالا `timeout` دارند (قبلاً `--max-time` کرل تنها ضمانت بود؛ اگر curl گیر می‌کرد، ترد برای همیشه می‌ماند).
- سقف تست همزمان روی ایجنت: ۶ → **۳**

اگر ربات و ایجنت روی یک ماشین‌اند، `CPUQuota=60%` یعنی همیشه ۴۰٪ برای ربات می‌ماند.
برای سخت‌گیری بیشتر: `SONAR_AGENT_CPU_QUOTA=40%`

### ۴. چرخه‌ی reconnect متوقف شد — `settings.py`, `monitor_agent.py`

`ping_timeout` هم در ربات و هم در ایجنت ۲۰ ثانیه بود. وقتی CPU نود اشباع می‌شد،
ایجنت نمی‌رسید به ping جواب بدهد و `websockets` **همه‌ی** کانکشن‌ها را با هم می‌بست.
ربات فوراً دوباره وصل می‌شد، ایجنت باز هم عقب می‌ماند، و چرخه تکرار می‌شد.

| | ۴.۲ | ۴.۳ |
|---|---|---|
| `ping_interval` | ۲۰ | ۳۰ |
| `ping_timeout` | ۲۰ | ۹۰ |

### ۵. سقف‌ها با ظرفیت واقعی ایجنت هم‌خوان شدند — `tunnel_logic.py`, `settings.py`

فرستادن ۲۰ تست همزمان به ایجنتی که فقط ۳ تا را موازی اجرا می‌کند فایده ندارد؛
۱۷ تا فقط معطل می‌مانند و تایم‌اوت می‌خورند.

| | ۴.۲ | ۴.۳ |
|---|---|---|
| `GLOBAL_TEST_LIMIT` | ۲۰ | ۸ |
| `PER_USER_TEST_LIMIT` | ۳ | ۲ |
| `WS_POOL_MAX_PER_KEY` | ۲۰ | ۱۰ |

## نصب

```bash
pip install -r requirements.txt
systemctl restart sonar-bot
```

بعد حتماً ایجنت را آپدیت کن (تغییرات `nice` و `CPUQuota` فقط با نصب مجدد سرویس اعمال می‌شوند):
**پنل ادمین ← مدیریت ایجنت ← نصب/آپدیت**

### اگر ربات و ایجنت یک‌جا هستند، این را هم بزن

```bash
systemctl edit sonar-bot
```
و اضافه کن:
```ini
[Service]
Nice=-5
CPUWeight=200
```
یعنی «ربات همیشه از ایجنت اولویت بیشتری دارد».

### متغیرهای محیطی

```bash
SONAR_AGENT_MAX_TESTS=3       # تست همزمان روی ایجنت
SONAR_AGENT_CPU_QUOTA=60%     # سقف CPU ایجنت
SONAR_GLOBAL_TEST_LIMIT=8     # سقف کل تست‌های در جریان
SONAR_USER_TEST_LIMIT=2       # سقف هر کاربر
SONAR_WS_POOL_MAX=10          # کانکشن همزمان به هر نود
```
