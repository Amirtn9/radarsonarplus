# راهنمای اصلاحات پایداری، Agent و لاگ‌ها — Sonar Radar Pro 6.6.0

## ۱. ترتیب ارتباط

1. سرور مرکزی همیشه اولین مسیر SSH است.
2. خطاهای شبکه/اتصال مقصد یا خرابی انتقال TLS/WebSocket خود Agent اجازه می‌دهند مسیر جایگزین امتحان شود. خطاهای `HOST_KEY_UNKNOWN`، `HOST_KEY_CHANGED` و خطای احراز هویت SSH مقصد با Agent دیگر دور زده نمی‌شوند.
3. مسیرهای جایگزین از استخر Agentهای تأییدشده در ایران و خارج انتخاب می‌شوند. Agent باید فعال، دارای توکن و گواهی TLS معتبر، تأییدشده و دارای heartbeat موفق در پنج دقیقه اخیر باشد.
4. اولویت عددی مسیرها از ۰ تا ۱۰۰۰ است؛ عدد کمتر یعنی اولویت بالاتر. در اولویت یکسان، سیاست latency/load/balanced امتیاز را مرتب می‌کند.
5. مقصدی که با Agent موفق شده تا ۳۰ دقیقه همان Agent را ترجیح می‌دهد. در شکست تکراری، مسیر برای مدت کوتاه از انتخاب خارج می‌شود تا تغییر مسیر و IP بی‌دلیل کاهش یابد.
6. اتصال SSH به‌صورت end-to-end از سمت کنترل‌کننده بررسی می‌شود. Agent فقط جریان SSH رمزگذاری‌شده را منتقل می‌کند و نباید اثرانگشت مقصد را تأیید یا جایگزین کند.

## ۲. محدوده دسترسی Agent و مالکیت

- نصب دسته‌ای Agent از پنل فقط روی سرورهای فعال متعلق به مدیر اصلی مجاز است.
- مالک دیگر باید Agent را روی سرور خودش نصب کند و صریحاً آن را برای اشتراک پیشنهاد دهد؛ سپس مدیر می‌تواند آن را تأیید کند.
- غیرفعال کردن Agent از استخر مسیرها، Agent را حذف نمی‌کند.
- Agentهای خارج از ایران از همان منطق مسیر و TLS استفاده می‌کنند؛ موقعیت جغرافیایی به‌تنهایی معیار اعتماد نیست.
- فقط IP عمومی و پورت‌های موجود در allowlist قابل استفاده در relay هستند. پورت‌های پیش‌فرض: `22,443,2022,2222,10022,22022`. برای پورت SSH سفارشی، روی سرور مرکزی با `sudo bash install.sh --set SONAR_AGENT_RELAY_PORTS 22,443,2022,2222,10022,22022,22222` مقدار را تنظیم کنید و Agentها را Repair/نصب مجدد کنید تا allowlist هر دو طرف هماهنگ شود.
- این معماری failover روی مسیرهای مجاز و قابل‌دسترسی ایجاد می‌کند؛ هیچ سامانه‌ای نمی‌تواند عبور از همه فایروال‌ها، NATها یا محدودیت‌های شبکه را تضمین کند.

## ۳. نصب پیش‌نیازها و خطای VENV_CREATE_FAILED

- تمام فرمان‌های مدیریتی روی مقصد از wrapper دارای `sudo -n` عبور می‌کنند؛ ورود SSH به‌عنوان `ubuntu` به معنی اجرای فرمان‌ها با دسترسی root نیست.
- بررسی `python3 -m venv --help` کافی نیست؛ نسخه جدید یک محیط آزمایشی واقعی در `/tmp` می‌سازد و `pip --version` را بررسی می‌کند.
- در صورت کمبود `ensurepip`، ابتدا `python3-venv` و سپس بسته نسخه دقیق Python مانند `python3.12-venv` نصب و مجدداً آزمایش می‌شوند.
- ساخت venv جدید در مسیر stage انجام می‌شود؛ محیط فعال قبلی تا زمان تأیید نسخه جدید حذف یا جایگزین نمی‌شود.
- بسته‌های Python ابتدا روی سرور مرکزی دانلود و هش SHA-256 آن‌ها بررسی می‌شود. انتقال SFTP ابتدا از مسیر SSH مستقیم و سپس از Agentهای مجاز انجام می‌شود. pip مستقیم روی مقصد تنها fallback نهایی است.
- اگر نصب بسته‌های سیستم از مخزن مقصد شکست بخورد، سیستم تلاش می‌کند URI و هش بسته‌های `.deb` را از طرح APT مقصد استخراج کند، آن‌ها را روی سرور مرکزی دانلود و با هش مخزن بررسی کند، سپس از همان مسیر SSH/Agent منتقل و با `apt-get --no-download` نصب کند. این مسیر فقط برای URIهای HTTP(S) عمومی و دارای هش معتبر استفاده می‌شود. اگر فهرست APT مقصد موجود نباشد، هش قابل بررسی نباشد یا مخزن خصوصی/غیرقابل دسترسی باشد، نصب به‌صورت امن متوقف می‌شود و نباید آن را دورزدن قطعی محدودیت شبکه تلقی کرد.

## ۴. اثرانگشت SSH و TLS

- اثرانگشت SSH مقصد پس از تطبیق مستقل و احراز هویت معتبر در مخزن `known_hosts` کنترل‌کننده ثبت می‌شود.
- هنگام عبور از Agent، SSH همچنان end-to-end است؛ Agent نباید کلید میزبان را تغییر دهد یا اعتماد خودکار ایجاد کند.
- `HOST_KEY_UNKNOWN` برای سرور قبلاً ثبت‌شده با اسکن اثرانگشت و تأیید مستقل حل می‌شود؛ حذف و افزودن دوباره سرور لازم نیست.
- `HOST_KEY_CHANGED` باید جداگانه بررسی شود؛ کلید جدید را صرفاً برای رفع خطا تأیید نکنید.
- اگر Agent به‌صورت `TLS-enrolled` ثبت نشده باشد، آن Agent تا نصب/تعمیر و تأیید WSS/TLS وارد استخر relay نمی‌شود.

## ۵. بسته لاگ هفت‌روزه

- پیش‌فرض پنل و ربات: هفت روز اخیر؛ پنل بازه‌های ۱، ۷، ۱۴ و ۳۰ روزه را نیز می‌پذیرد.
- بسته شامل journal ربات و پنل، لاگ خطا، لاگ نصب، فایل‌های کاربردی چرخشی، وضعیت عملیاتی سرورها/Agentها/کارهای نصب و journal تمام سرورهای ذخیره‌شده است.
- برای لاگ‌های محلی و راه‌دور هیچ `tail -n` یا سقف تعداد خط اعمال نمی‌شود. فقط بازه زمانی انتخاب‌شده لحاظ می‌شود.
- خطوط و stack traceها حذف نمی‌شوند؛ مقادیر محرمانه در همان خط پوشانده می‌شوند. فایل‌های اصلی روی سرور حذف یا تغییر نمی‌کنند.
- اگر دسترسی journal یا فایل نصب محدود باشد، ابزار خواندن محدود و root-owned از طریق sudoers اجرا می‌شود. این helper فقط سرویس‌ها و فایل‌های allowlistشده را می‌خواند و فرمان دلخواه اجرا نمی‌کند.
- اگر سرور مقصد در دسترس نباشد یا کلید SSH تأیید نشده باشد، فایل ZIP وضعیت خطا را برای همان سرور ثبت می‌کند؛ امنیت SSH برای جمع‌آوری لاگ دور زده نمی‌شود.

## ۶. پنل وب

- داشبورد همچنان صفحه آغازین است.
- «سرورها» و «کانفیگ‌ها» از هم جدا هستند.
- صفحه «بالانسر مسیرها» برای مدیر، Agentهای ایران و خارج، وضعیت TLS، اولویت، سلامت و ترتیب مسیرهای پشتیبان را نشان می‌دهد.
- سیاست انتخاب مسیر و اولویت Agent قابل مدیریت است؛ دسترسی APIها همچنان از کنترل نقش مدیر و نشست معتبر عبور می‌کند.
- بسته تشخیصی فقط برای مدیر اصلی قابل دریافت است و فایل خروجی با مجوز خصوصی ساخته می‌شود.

## ۷. بررسی پس از استقرار

1. از دیتابیس، `secret.key`، `known_hosts` و فایل‌های تنظیمات پشتیبان بگیرید.
2. پروژه را در محیط staging اجرا کنید و ابتدا یک سرور متعلق به مدیر را اضافه کنید.
3. اثرانگشت را از کنسول خود سرور بخوانید و با مقدار پنل تطبیق دهید.
4. نصب/Repair Agent را اجرا کنید؛ وضعیت TLS-enrolled و WSS را بررسی کنید.
5. ارتباط مستقیم را موقتاً در محیط آزمایش قطع کنید و تأیید کنید Agent اول انتخاب می‌شود؛ سپس Agent اول را از استخر خارج کنید و مسیر بعدی را تست کنید.
6. از پنل یک ZIP هفت‌روزه بگیرید و وجود `logs/bot.log`، `logs/web.log`، `logs/install.log`، `state/operational-state.json` و فایل‌های `agents/server-*.log` را بررسی کنید.

آزمون‌های خودکار مسیر failover، نصب آفلاین، حفظ خط‌های لاگ و مالکیت Agent اجرا می‌شوند؛ تأیید نهایی به تست SSH/TLS واقعی روی سرورهای شما نیاز دارد.
