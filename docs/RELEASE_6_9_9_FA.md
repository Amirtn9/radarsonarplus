# نسخه ۶.۹.۹ — اعتبارسنجی گزارش امنیتی پیشنهادی

تاریخ: 2026-11-10. مبنا: نسخه ۶.۹.۸، commit `c1b3e40`. متن ارسالی کاربر مجموعه‌ای از ادعاهای باگ و پیشنهادهای توسعه است؛ هیچ‌یک بدون بررسی کد، تأییدشده فرض نشده است.

## ایرادهای تأییدشده و اصلاح‌شده

| مورد | نتیجه و اصلاح |
|---|---|
| تبدیل bytes در encrypt | تأیید شد؛ UTF-8 bytes مستقیماً رمز می‌شود و بعد از decrypt همان متن بازمی‌گردد. انواع غیرمتنی و bytes نامعتبر پیش از ذخیره رد می‌شوند. ciphertextهای قدیمی تغییر نمی‌کنند. |
| فایل‌سیستم بدون hard link | تأیید شد؛ خطاهای مشخص عدم پشتیبانی به ساخت O_EXCL برمی‌گردند. همه خواننده‌ها و سازنده‌های کلید قفل مشترک flock می‌گیرند تا کلید نیمه‌نوشته خوانده نشود. Permission denied واقعی پوشانده نمی‌شود. پشتیبانی از descriptorها و flock لینوکس لازم است؛ این ادعای سازگاری همه NFSها نیست. |
| symlink والد و TOCTOU | تأیید شد؛ کل مسیر با descriptor پوشه و O_NOFOLLOW پیمایش می‌شود. پوشه‌ها از همان descriptor ساخته می‌شوند؛ فایل کلید و lock باید regular و تک‌لینکی باشند. hard link کلید پیش از chmod رد می‌شود. |
| مصرف سهمیه با ورود موفق و مرز پنجره | تأیید شد؛ هر ورود یک reservation می‌گیرد و ورود موفق فقط همان یک واحد را آزاد می‌کند. خطاهای قبلی پاک نمی‌شوند. محدودیت بعد از ۱۵ دقیقه بدون تلاش بازنشانی می‌شود، نه در مرز ثابت از اولین درخواست. این سیاست محافظه‌کارانه، sliding-window دقیق آماری نیست و حذف کامل اثر NAT را تضمین نمی‌کند. |
| رشد جدول تلاش ورود | تأیید شد؛ رکوردهای بیش از یک روز در مسیر ورود حذف می‌شوند و index زمان دارند. |
| نبود index انقضای session | تأیید شد؛ migration افزایشی ۱۵، index انقضای session، انقضای code، کدهای هر کاربر و زمان تلاش ورود را اضافه می‌کند. migrationهای منتشرشده قبلی دست‌نخورده‌اند. |
| باطل شدن لینک اول با کلیک دوم | رفتار قبلی تأیید شد؛ اکنون حداکثر سه کد زنده اخیر هر کاربر حفظ می‌شوند. صدور با قفل تراکنشی سریال است؛ مصرف هر کد همچنان یک‌بارمصرف و اتمیک است. logout_all همه کدها را باطل می‌کند. |
| دو poller با یک توکن | نبود قفل تأیید شد؛ پیش از run_polling یک advisory lock بر اساس توکن گرفته و در خروج آزاد می‌شود. تست واقعی PostgreSQL اجرای دوم با همان توکن را رد می‌کند و توکن دیگر را مستقل می‌پذیرد. محدوده قفل همان دیتابیس است؛ دو دیتابیس مستقل یا از دست رفتن اتصال نگه‌دارنده، تحت تضمین fencing توزیع‌شده قرار ندارند. |
| سیل هشدار سرویس‌ها | نبود pacing مشترک تأیید شد؛ مسیر notifications پیام‌ها را برای هر chat، مستقل از topic، با فاصله پیش‌فرض ۱٫۰۵ ثانیه ارسال می‌کند. RetryAfter تلگرام با حداکثر یک retry و تأخیر اعلام‌شده رعایت می‌شود؛ تأخیر بیش از ۱۲۰ ثانیه به مسیر retry صف واگذار می‌شود. همه ارسال‌های مستقیم و نامرتبط ربات از این helper عبور نمی‌کنند؛ grouping سراسری و تشخیص خرابی شبکه کنترل‌کننده هنوز اضافه نشده است. |

هیچ کلید موجودی rotate یا جایگزین نشده، هیچ credential یا بکاپ مشتری بازنویسی نشده و هیچ سرویس واقعی راه دور تغییر نکرده است.

## ادعاهای تأییدنشده، ازقبل پوشش‌داده‌شده یا نیازمند تفکیک

| ادعا | نتیجه بررسی |
|---|---|
| None و رمز خالی همیشه در ذخیره یکی هستند | دقیق نیست: encrypt(None) sentinel خالی می‌دهد، اما encrypt('') یک ciphertext معتبر غیرخالی می‌سازد. decrypt برای سازگاری مسیرهای SSH هر دو را به متن خالی نرمال می‌کند؛ تغییر ناگهانی قرارداد None اعمال نشده است. |
| session حساب حذف/مسدود تا ۸ ساعت مجاز می‌ماند | در API فعلی تأیید نشد؛ actor پس از identify، در هر درخواست db.check_access را بررسی و حساب نامعتبر را رد می‌کند. انقضا و ban در Database.check_access کنترل می‌شوند. |
| CSRF بررسی نمی‌شود | رد شد؛ Origin برای cookie auth و مقایسه digest توکن CSRF با secrets.compare_digest از قبل وجود دارد. |
| initData هشت ساعت معتبر است | رد شد؛ پنجره initData پیش‌فرض ۳۰۰ ثانیه و سقف تنظیم‌پذیر آن ۶۰۰ ثانیه است. session cookie جداگانه هشت‌ساعته است. |
| SSRF HTTP/TCP و rebinding/redirect آزاد است | با پیش‌فرض فعلی تأیید نشد؛ service_probes آدرس عمومی را در زمان اتصال resolve و همان IP را pin می‌کند، TLS نام میزبان را بررسی می‌کند و redirect دنبال نمی‌شود. گزینه صریح SONAR_SERVICE_ALLOW_PRIVATE=1، تصمیم اپراتور برای شبکه خصوصی است. |
| Agent یک relay عمومی برای private IP است | تأیید نشد؛ valid_relay_destination فقط IP عمومی literal و پورت‌های allowlist را می‌پذیرد. Agent نیازمند token و گواهی TLS pin‌شده است؛ SSH host key مقصد end-to-end بررسی می‌شود. استفاده از نود مشترکِ تأییدشده مدیر یک قابلیت عمدی است و الزام مالک یکسان، سیاست فعلی نیست. |
| fallback fingerprint مقصد را تغییر می‌دهد | در مسیر بررسی‌شده تأیید نشد؛ Paramiko مقصد نهایی و host key ذخیره‌شده را مستقل از کانال relay کنترل می‌کند. تغییر pin یا خاموش کردن بررسی host key اعمال نشده است. |
| نوسان هشدار بدون آستانه است | رد شد؛ failure_threshold و recovery_threshold، شمارنده‌ها و state machine سرویس از قبل وجود دارند. |
| migration بدون هیچ مسیر بازیابی است | ادعای مطلق درست نیست؛ migration تراکنشی، ledger، قفل مشترک، بکاپ قبل ارتقای installer و تست restore واقعی وجود دارند. downgrade خودکار schema و تحمل همه انواع crash ادعا نشده است. |
| بکاپ همیشه کلید و دیتابیس را بدون حفاظت کنار هم می‌فرستد | نیازمند تفکیک: مسیر Enterprise با SONAR_BACKUP_ENCRYPTION_KEY مستقل، pg_dump را رمز می‌کند. مسیر نصب/بازیابی محلی sidecar کلید متناظر دارد؛ نگهداری جداگانه/رمزکردن آن همچنان مسئولیت عملیاتی مهمی است و این انتشار فرمت بکاپ موجود را عوض نمی‌کند. |
| هیچ وابستگی hash-lock نشده | برای CI رد شد؛ lockهای کامل Python 3.10/3.11/3.12 همراه hash و package-lock برای Playwright موجودند. متن قدیمی README که خلاف این را می‌گفت اصلاح شد. پوشش تمام سیستم‌عامل‌ها و افزونه S3 ادعا نمی‌شود. |
| HMAC webhook، health و maintenance وجود ندارند | کلیت ادعا درست نیست؛ HMAC و رمزگذاری secret webhook، healthz/readyz، وضعیت و سیاست اعلان وجود دارند. Prometheus و همه انواع probe پیشنهادی از این موضوع نتیجه نمی‌شوند. |

## بررسی تاریخچه و وابستگی‌ها

Gitleaks نسخه ۸.۲۴.۳ از انتشار رسمی، پس از تأیید SHA-256 آرشیو اجرا شد. clone shallow نبود؛ اسکن با `git --log-opts=--all --redact=100` انجام شد. ابزار ۲۷ commit دارای diff را از refs موجود بررسی کرد (git log --all در زمان بررسی ۳۴ commit نشان می‌داد). اسکن اول ۷۱ تطبیق generic-api-key داشت که همگی assignmentهای keyboard escape در نسخه تاریخی xterm.js بودند؛ تک‌تک محل‌ها بررسی شدند و secret نبودند.

فقط fingerprint همان commit/file/rule/line در `.gitleaksignore` ثبت شده؛ کل vendor یا rule غیرفعال نشده و commitهای آینده همچنان بررسی می‌شوند. اجرای مجدد مورد حل‌نشده‌ای گزارش نکرد. این نتیجه ضمانت نبود هر نوع secret ناشناخته یا پوشش refs حذف‌شده از سرور نیست. گزارش خام و مقادیر احتمالی وارد Git نشده‌اند. تنظیمات Dependabot برای pip، npm و GitHub Actions اضافه شد؛ فعال بودن Secret Scanning در تنظیمات میزبان GitHub ادعا نمی‌شود. به‌روزرسانی Python نیازمند بازتولید lockهای hashدار نیز هست.

## پیشنهادهای توسعه و محدودیت‌های باقی‌مانده

موارد زیر با «باگ رفع‌شده» یکی نیستند و در این انتشار پیاده‌سازی نشده‌اند:

- چرخش کامل کلید با MultiFernet و migration داده، اتصال ciphertext به context ردیف، و سیاست بازنشستگی کلید. تغییر صرف encrypt بدون مهاجرت تمام مصرف‌کننده‌ها و بکاپ‌ها می‌تواند credentialهای موجود را غیرقابل بازیابی کند.
- 2FA/step-up برای عملیات حساس، idle timeout و rotation نشست، و مصرف یک‌باره initData در مبادله session. initData در طول پنجره کوتاه فعلی قابل استفاده مجدد است؛ این محدودیت مستند است و نشانه معتبرتر بودن داده بعد از انقضا نیست.
- تگ امضاشده و مدیریت کلید امضای انتشار، LICENSE منتخب مالک، Secret Scanning حساب، CI کامل CodeQL/Bandit/pip-audit/shellcheck و sshd/container واقعی. کلید امضا یا شرایط مجوزی اختراع نشده و تنظیمات حساب مالک بی‌مدرک فعال‌شده اعلام نمی‌شوند.
- audit log واقعاً تغییرناپذیر در برابر مدیر دیتابیس، اجبار حساب کم‌امتیاز برای همه سرورهای موجود، SSH Certificate/Vault، Docker/Compose، انتقال ساختار به src، استانداردگذاری یکپارچه ruff/mypy، RBAC گسترده‌تر، فهرست دستگاه‌های نشست، Prometheus و تکمیل همه probeهای پیشنهادی.
- allowlist داده ساختاریافته گزارش عملیاتی و canaryهای redaction وجود دارند، ولی لاگ متن آزاد و stack trace را نمی‌توان بدون حذف اطلاعات تشخیصی صرفاً به فیلدهای ثابت محدود کرد. بررسی انسانی ZIP پیش از اشتراک همچنان لازم است.

این گزارش تأیید امنیت صددرصدی، اجرای pentest روی سرور مشتری یا رفع همه پیشنهادهای توسعه‌ای متن ارسالی نیست.

## آزمون‌ها

۵۱۰ تست مجموعه کامل روی Python 3.10، 3.11 و 3.12، با PostgreSQL واقعی و هر دو Xray قفل‌شده، موفق شدند. سناریوی هم‌زمانی ساخت کلید سپس علاوه بر حالت عادی، با عدم پشتیبانی اجباری hard link نیز جداگانه موفق شد؛ CI مجموع ۵۱۱ تست را اجرا می‌کند. چهار سناریوی مرورگر نیز موفق بودند. آزمون‌های جدید شامل حفظ bytes، رد symlink اجداد و hard link کلید، حفظ چند کد یک‌بارمصرف، پاک‌سازی و سهمیه ورود، indexهای migration ۱۵، انحصار poller و رعایت فاصله/RetryAfter هشدار هستند. syntax، compilation، dependency check، preflight و manifest نیز موفق بودند. ارتقای VPS مشتری، تعویض واقعی کلید و تنظیمات امنیتی حساب GitHub آزمایش نشده‌اند.
