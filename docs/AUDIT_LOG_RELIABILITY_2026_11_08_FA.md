## دامنه و وضعیت واقعی مأموریت

این تغییر، اصلاح عملی و آزموده‌شده پایداری Agent و مدیریت لاگ‌های **پایگاه داده** است؛ تأیید بی‌قیدوشرط تمام پروژه یا پایان تمام بندهای مأموریت اولیه نیست. اتصال PasarGuard و شمارنده کاربران آنلاین آن در این مخزن پیدا نشد؛ آمار موجود، CPU/RAM/دیسک/ترافیک و وضعیت سرور و Agent است. بنابراین رفع مشکل کاربران آنلاین PasarGuard ادعا نمی‌شود.

فهرست خودکار نهایی ۲۷۸ فایل را پوشش می‌دهد؛ ۱۳۷ فایل Python با AST/کامپایل کنترل شدند. بازبینی هدفمند سورس شامل مسیرهای پایش، WebSocket، ذخیره آمار، لاگ، احراز هویت وب، دسترسی فضای کاری، migration، گزارش، نصب و بسته‌بندی و آزمون‌های مربوط بود. این اعداد به معنی بازبینی دستی خط‌به‌خط همه ۲۷۸ فایل نیستند. تغییرات نهایی در ۲۲ فایل موجود و ۶ فایل جدید قرار دارند.

## معماری بررسی‌شده

ربات Telegram و پنل FastAPI از PostgreSQL، ledger مشترک migration و قفل advisory مشترک استفاده می‌کنند. پایش ابتدا از WSS با گواهی ثبت‌شده Agent استفاده می‌کند و مسیر SSH نقش fallback دارد. برنامه وب و Mini App رابط مشترک دارند؛ نشست کوکی با Origin و CSRF کنترل می‌شود و initData تلگرام امضاشده است. کوئری‌های کاربران و منابع با مالک/فضای کاری محدود می‌شوند. سرویس‌های پس‌زمینه شامل مشاهده سرورها، عملیات، webhook، بازیابی، rollout و backup هستند. این تغییر معماری موجود را حفظ می‌کند.

## مدیریت لاگ جدید

در بخش «عیب‌یابی مدیر»، مدیریت لاگ پایگاه داده افزوده شده است:

- بازه‌های ۲۴ ساعت، ۴۸ ساعت، ۷ روز، همه رکوردهای موجود و بازه دلخواه؛ مرجع، زمان واقعی ایجاد رکورد است.
- سطح‌های DEBUG/INFO/WARNING/ERROR/CRITICAL و دسته‌های API، Node، Authentication، Database، System و User Activity.
- زمان UTC، منبع، پیام/stack trace پاک‌سازی‌شده و وضعیت ثبت/خطا؛ نمایش تاریخ در زمان محلی دستگاه و تبدیل بازه انتخابی به UTC.
- صفحه‌بندی ۵۰تایی پیش‌فرض و حداکثر ۱۰۰ رکورد در API؛ index زمانی و ترکیبی.
- صف حداکثر ۲۰۰۰ رکورد، دسته نوشتن حداکثر ۱۰۰ رکورد، پیام حداکثر ۱۶۰۰۰ کاراکتر؛ هیچ انتظار PostgreSQL در emit روی event loop انجام نمی‌شود.
- نگهداری لاگ برنامه ۳۰ روز و audit ۹۰ روز با پاک‌سازی دسته‌ای؛ شمارش‌ها مستقیم از دیتابیس خوانده می‌شوند، نه cache دائمی.
- درخواست‌های تغییردهنده API و خطاها با الگوی route، status و زمان پردازش ثبت می‌شوند؛ query، body، توکن و شناسه متغیر مسیر ثبت نمی‌شوند. polling موفق تکراری لاگ اضافی تولید نمی‌کند.
- خواندن و حذف لاگ کل سیستم فقط با `SUPER_ADMIN_ID` در سرور مجاز است؛ manager یا مالک یک فضای کاری این مجوز را ندارد.

### پاک‌سازی و هم‌زمانی

حذف نیازمند تأیید مرورگر و واردکردن دقیق `DELETE ALL LOGS` است. API DELETE علاوه بر کنترل مدیر اصلی، برای نشست کوکی همان کنترل Origin/CSRF را دارد. خود API نیز عبارت تأیید را بررسی می‌کند.

فقط `pro_application_logs` و `pro_audit`، شامل فعالیت همه کاربران، در یک تراکنش حذف می‌شوند. هیچ `TRUNCATE CASCADE`، حذف فایل یا حذف جدول عملیاتی وجود ندارد. قفل advisory و قفل جدول، حذف و نوشتن را هماهنگ می‌کنند. watermark مشترک در `pro_log_state` مانع بازگشت رکوردهای قدیمی صف از تمام پردازش‌ها می‌شود. شمارنده‌های نمایشی از رکوردهای باقی‌مانده محاسبه می‌شوند و پاسخ‌های قدیمی در حال دریافت در رابط بی‌اعتبار می‌شوند. رکورد واقعاً جدید بعد از پاک‌سازی مجاز است و با داده قدیمی فرق دارد.

**محدودیت مهم:** این دکمه فایل‌های چرخشی، journal سیستم، لاگ نصب یا لاگ روی Nodeهای دور را حذف نمی‌کند. بنابراین «حذف همه لاگ‌ها از تمام منابع» هنوز تکمیل نشده است. این منابع همچنان در خروجی عیب‌یابی قابل دریافت‌اند. پاک‌سازی journal مشترک به‌صورت کلی می‌تواند لاگ سایر سرویس‌ها را از بین ببرد؛ چنین حذف گسترده‌ای اضافه نشده است.

### محدودیت‌های عملکردی

ثبت دیتابیس best-effort است: در پرشدن صف یا قطعی دیتابیس ممکن است batch حذف شود؛ خطای worker با شمارنده dropped و بدون متن حساس، حداکثر یک‌بار در دقیقه در مسیرهای معمول لاگ گزارش می‌شود. این صف، ذخیره تضمینی یا جایگزین file/journal نیست. نگهداری زمانی و صف محدود، تضمین ظرفیت دیسک تحت بار دلخواه نیست؛ بار واقعی و نرخ تولید لاگ باید روی staging اندازه‌گیری شود. توکن قدیمی داخل متن غیرساختاریافته بدون نام/الگوی قابل‌شناسایی الزاماً قابل‌تشخیص نیست.

## دیتابیس و ارتقا

Migration افزایشی **۱۳ / log_management** به registry موجود اضافه شده است و migrationهای قبلی تغییر نکرده‌اند. دو جدول جدید `pro_application_logs` و `pro_log_state` و دو index اضافه می‌شوند؛ audit قبلی حفظ می‌شود و با UNION ALL خوانده می‌شود. هیچ حذف داده در migration وجود ندارد. نوشتن لاگ دیتابیس بعد از موفقیت migration در Bot و Web فعال می‌شود و هنگام shutdown جدا می‌شود.

قبل از ارتقای عملیاتی، backup PostgreSQL و `secret.key` متناظر را طبق runbook موجود نگه دارید. بازگشت عملیاتی، restore همان backup همراه کد و کلید متناظر است؛ reverse migration مخرب اجرا نشده است. نصب کامل systemd، فایروال، TLS عمومی و ارتقای سرور واقعی در این محیط انجام نشده‌اند.

## موارد انجام‌نشده و نیازمند محیط واقعی

اتصال/آمار کاربران PasarGuard به علت نبود این زیرسیستم در مخزن؛ پاک‌سازی همه منابع file/journal/remote؛ ارتباط واقعی با Node مشتری و بازیابی شبکه ایران؛ ارسال واقعی Telegram، webhook و آزمون کانفیگ مشتری؛ نصب و ارتقای کامل VPS با systemd و ACME؛ آزمون بار طولانی CPU/RAM/DB و سنجش نشت حافظه؛ بازبینی امنیت مستقل و خط‌به‌خط تمام سورس.

این موارد حل‌شده یا تست‌شده اعلام نمی‌شوند. هیچ مدرکی برای اعلام «تمام پروژه بدون باگ/کاملاً امن» وجود ندارد. ارتقای سرور عملیاتی یا حذف لاگ واقعی در این مأموریت اجرا نشده است.
