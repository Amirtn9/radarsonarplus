# مهاجرت نسخه‌دار دیتابیس

در نسخه 6.9.2 یک ledger مشترک به نام `sonar_schema_migrations` اضافه شده است.

## ترتیب اجرا

1. `Database.init_db()` با قفل تراکنشی PostgreSQL و نسخه `1 / core_schema` اسکیمای پایه را فقط یک بار ایجاد می‌کند.
2. `schema_migrations.run_startup_migrations()` مهاجرت‌های افزایشی نسخه‌های 2 تا 11 را اجرا می‌کند.
3. ربات تلگرام و API وب دقیقاً از همین رجیستری و قفل session-level با شناسه `535300` استفاده می‌کنند؛ شروع هم‌زمان دو سرویس نباید DDL را هم‌زمان اجرا کند.
4. هر مهاجرت پس از موفقیت در جدول ledger ثبت می‌شود. اگر فرایند قبل از ثبت نسخه قطع شود، callbackهای DDL idempotent هستند و اجرای دوباره باید امن باشد.

## قانون تغییرات بعدی

- مهاجرت منتشرشده را ویرایش یا شماره آن را دوباره استفاده نکنید.
- برای هر تغییر اسکیمای جدید، یک شماره بزرگ‌تر و callback مستقل اضافه کنید.
- callback باید قابل اجرای دوباره باشد و در صورت شکست، خطای واقعی را بالا ببرد.
- عملیات نگهداری تکرارشونده را در callback یک‌باره قرار ندهید؛ آن‌ها را به worker یا startup maintenance جدا منتقل کنید.
- rollback خودکار با حدس زدن `DROP`/`ALTER` انجام نمی‌شود. پیش از ارتقا، Backup تأییدشده بسازید و در صورت نیاز دیتابیس و `secret.key` هم‌نام را با هم بازیابی کنید.

## محدودیت اعتبارسنجی

تست واحد runner و قفل در این بسته اجرا می‌شود؛ آزمون واقعی رقابت دو پروسس Bot/Web، اجرای SQL روی PostgreSQL و بازیابی کامل باید در staging دارای PostgreSQL انجام شود.
