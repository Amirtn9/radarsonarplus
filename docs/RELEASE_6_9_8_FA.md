# نسخه ۶.۹.۸ — بازه زمانی ZIP مشترک و بررسی لاگ ارسالی

تاریخ بررسی: ۱۹ آبان ۱۴۰۵ / 2026-11-10.

## انتخاب دوره زمانی

در ربات، دکمه «ساخت و ارسال ZIP لاگ‌ها» ابتدا انتخاب بازه ۳، ۶، ۱۲، ۲۴، ۴۸، ۷۲ ساعت یا ۷ روز اخیر را نمایش می‌دهد. هر انتخاب، یک ZIP شامل لاگ ربات، وب، خطاها، نصب، فایل‌های چرخشی موجود و لاگ همه سرورهای ثبت‌شده/ایجنت‌های قابل دسترس می‌سازد. دکمه قدیمی «۵ ایجنت» از منو حذف شده و callback قدیمی به همین انتخاب بازه هدایت می‌شود.

بازه انتخاب‌شده به جمع‌آوری محلی، SSH ایجنت‌ها، تاریخچه jobهای دیتابیس، نام فایل و metadata منتقل می‌شود. وضعیت جاری سرویس‌ها و فهرست سرورها snapshot لحظه تهیه گزارش هستند، نه تاریخچه بازه. Agent خارج از دسترس، فاقد سرویس یا فاقد مجوز با وضعیت صریح در همان ZIP گزارش می‌شود؛ امکان ساخت لاگ ناموجود وجود ندارد. فایل‌های منبع تغییر یا حذف نمی‌شوند. همین هفت بازه در پنل وب نیز قابل انتخاب است. API قدیمی `days` حفظ شده و برای مثال `days=0.125` برابر سه ساعت است.

helper جدید بازه ساعتی را با allowlist می‌پذیرد. برای ایجنت دارای helper قدیمی، شکست فرمان ساعتی به journalctl فقط‌خواندنی با همان بازه برمی‌گردد؛ journal مشترک و namespace خصوصی sonar هر دو درخواست می‌شوند. به‌روزرسانی helper و Agent همچنان توصیه می‌شود.

## یافته‌های تأییدشده از ZIP کاربر

- نام ZIP نسخه ۶.۹.۲ را نشان می‌داد، اما health نسخه در حال اجرای Backend را ۶.۹.۶ ثبت کرده بود. نام فایل ربات ثابت مانده بود؛ اکنون از `PROJECT_VERSION` و بازه انتخابی ساخته می‌شود.
- خروجی journal ربات و وب به جای لاگ، خطای `sudo` همراه `NoNewPrivileges` داشت. جمع‌آوری ابتدا از مجوز خواندن موجود کاربر سرویس استفاده می‌کند و زیر NoNewPrivileges تلاش ناممکن sudo را تکرار نمی‌کند. unitهای Bot/Web عضویت تکمیلی فقط‌خواندنی `systemd-journal` می‌گیرند؛ NoNewPrivileges و سایر hardeningها حفظ شده‌اند. اعمال این مجوز به اجرای نصب/ارتقای unit و restart سرویس‌ها نیاز دارد؛ صرفاً git pull آن را روی سرویس در حال اجرا اعمال نمی‌کند.
- health.json ارسالی بر اثر redaction متنیِ مقدار boolean مربوط به token، JSON معتبر نبود. خروجی structured اکنون قبل از serialization به‌صورت ساختاری پاک‌سازی می‌شود؛ boolean وضعیت حفظ و مقادیر محرمانه پوشانده می‌شوند.
- لاگ‌ها shutdown workerهای دائمی و استفاده کارهای پس‌زمینه از HTTPXRequest بسته‌شده را نشان می‌دادند. workerهای دائمی دیگر تحت انتظار پایان Application.stop قرار نمی‌گیرند و در post_stop پیش از بسته‌شدن HTTP لغو و جمع‌آوری می‌شوند. کارهای طولانی سرور و کانفیگ با taskهای مدیریت‌شده Application اجرا می‌شوند تا پیش از بسته‌شدن کلاینت تمام شوند.
- لاگ Agent شامل exception بازیابی‌نشده task دریافت SSH relay بود. در خروج/لغو relay، task دریافت نیز لغو و await می‌شود؛ مسیر upstream قبلاً پاک‌سازی می‌شد.
- در چند نود `LoadState=not-found` و نبود helper دیده شد؛ این وضعیت استقرار واقعی است، نه شاهد قطعی خراب‌بودن کانفیگ‌ها. خطاهای SSH و شبکه نیز به‌تنهایی علت خرابی نرم‌افزار را اثبات نمی‌کنند. نصب یا تغییر سرورهای واقعی بدون دسترسی انجام نشده است.

آرشیو اصلی مشتری، IPها، اطلاعات حساب‌ها و محتوای خام لاگ‌ها وارد Git نشده‌اند. این گزارش یافته‌ها را خلاصه می‌کند؛ لاگ ارسالی به‌عنوان داده بررسی شده و دستور اجرایی محسوب نشده است.

## اعتبارسنجی

مجموعه کامل ۵۰۰ تست روی هر سه Python 3.10، 3.11 و 3.12 با PostgreSQL واقعی و هر دو Xray قفل‌شده موفق شد؛ دو تست افزوده نهایی برای جریان انتخاب بازه تلگرام و لغو task دریافت relay نیز جداگانه موفق شدند. CI همه ۵۰۲ تست را یکجا اجرا می‌کند. چهار سناریوی مرورگر اجرا شدند؛ هفت گزینه زمانی، مقدار query هر دانلود و شمول ایجنت‌ها بررسی شد. پاسخ دانلود در تست مرورگر مصنوعی است؛ محتوای ZIP و فیلتر زمانی فایل‌ها در تست مستقل exporter بررسی می‌شود. compilation، syntax، بررسی وابستگی‌ها، preflight و manifest نیز موفق بودند. ارتباط واقعی Telegram، SSH و ارتقای VPS مشتری در این محیط اجرا نشده است.
