# گزارش بررسی و اصلاح SONAR RADAR PRO 6.9.2

تاریخ: ۲۰۲۶-۱۱-۰۴

## مبنا و محدوده

مبنای این بررسی فایل ارسالی `SONAR-RADAR-PRO-6.9.2-SECURITY-HARDENED.zip` است، نه صرفاً شاخهٔ `main`. صحت manifest نسخهٔ اصلی پیش از اصلاح تأیید شد: ۲۴۳ فایل منبع. SHA-256 فایل ورودی:

```text
ce1747c9310a18c491ce8d8da943e8cddfc878478bc4392d9cd7387e05af3655
```

از فایل‌های ZIP، ۱۷۷ فایل با checkout یکسان، ۴۷ فایل متفاوت و ۲۰ فایل مختص ZIP بود. بنابراین بخشی از تفاوت Git فعلی، انتقال نسخهٔ ارسالی به checkout است؛ این موارد نباید به‌عنوان اصلاحات تازهٔ این بررسی شمرده شوند. چهار فایل راهنمای patch/تعمیر manifest متعلق به ساختار قدیمی از ریشه کنار گذاشته شدند؛ راهنماهای تاریخی نسخهٔ ارسالی در `docs/archive/patch-history/` موجودند. نسخهٔ اولیهٔ این چهار فایل نیز خارج از checkout در `/workspace/.setup/legacy-main/` محفوظ است.

کدهای نصب و به‌روزرسانی، مهاجرت‌های دیتابیس، رمزنگاری و SSH، وب و Mini App، گزارش PDF، صف‌های عملیاتی، Agent و تست‌های موجود بررسی شدند. قابلیت محصول، سیاست اعتماد SSH، اولویت اتصال مستقیم، مجوزهای کاربران و قالب داده‌های رمز‌شده بدون دلیل تغییر نکردند. این بررسی ادعای اثبات نبود تمام خطاهای ممکن را ندارد.

## اصلاحات جدید این بررسی

| بخش | مشکل و اصلاح | اعتبارسنجی |
| --- | --- | --- |
| کلید رمزنگاری | ایجاد مستقیم `secret.key` می‌توانست فایل خالی/ناتمام را در شروع هم‌زمان Bot/Web در دسترس بگذارد. کلید اکنون در فایل خصوصی موقت نوشته و fsync می‌شود، سپس با hard link اتمیک و بدون جایگزینی کلید موجود منتشر می‌شود. | تست رقابت کنترل‌شدهٔ دو سازنده، بررسی خواندن رمز یکدیگر و حذف فایل‌های موقت |
| فایل غیرعادی کلید | بازکردن FIFO پیش از تشخیص نوع فایل می‌توانست startup را متوقف کند. خواندن nonblocking و کنترل regular file اعمال شد. | تست واقعی FIFO و ردشدن فوری |
| فایل موقت بکاپ | نام ثابت `.tmp` با `O_TRUNC` امکان دنبال‌کردن symlink یا برخورد دو writer را داشت. از `mkstemp` با مجوز 0600، جایگزینی اتمیک و cleanup استفاده شد. | تست symlink به فایل مستقل؛ محتوای آن دست‌نخورده ماند |
| بازیابی دیتابیس | بازیابی چندمرحله‌ای می‌توانست پس از خطای SQL، تغییرات ناقص باقی بگذارد. مسیرهای restore نصب‌کننده و بکاپ رمز‌شده با `--single-transaction` و توقف در خطا اجرا می‌شوند. | dump/restore واقعی و تزریق خطای وابستگی view؛ دادهٔ پیش از بازیابی ناموفق حفظ شد |
| rollback نصب Agent | تصمیم راه‌اندازی دوباره به وجود فایل sudoers وابسته بود؛ نصب قبلی با کاربر root ممکن بود به‌اشتباه متوقف بماند. تصمیم اکنون بر مبنای unit سرویس بازیابی‌شده است. | اجرای کد تولیدشدهٔ rollback در پوشهٔ موقت و بررسی فرمان restart |
| اعتبارسنجی Mini App | hash غیر ASCII می‌توانست در `compare_digest` استثنای نامناسب ایجاد کند. طول و حروف hex امضا پیش از مقایسه کنترل می‌شوند. | ورودی‌های Unicode و امضای نامعتبر به خطای احراز هویت تبدیل شدند |
| چرخهٔ عمر وب | بستن event loop وب، executor مشترک فرایند را هم می‌بست و ارسال کارهای بعدی شکست می‌خورد. executor پیش‌فرض وب اکنون مستقل و محدود به تعداد worker تنظیم‌شده است. | بعد از خروج از lifespan واقعی وب، executor مشترک همچنان کار اجرا می‌کند |
| readiness | نبود توکن ربات، به علت short-circuit، به‌اشتباه خرابی دیتابیس گزارش می‌شد. وضعیت دیتابیس و احراز هویت جداگانه بررسی و گزارش می‌شوند. | پاسخ مورد انتظار بدون توکن: HTTP 503، `db=ok` و `auth=unconfigured`؛ با توکن آزمایشی و دیتابیس سالم: 200 |
| تست‌های Agent و Router | شبیه‌ساز قدیمی Agent پاسخ preflight وابستگی‌ها را نداشت. دو تست Router نیز به جزئیات داخلی FastAPI وابسته بودند. شبیه‌سازی مرحلهٔ وابستگی تفکیک و ثبت مسیرها با درخواست واقعی HTTP/WebSocket بررسی شد. | تست‌های موجود با assertionهای رفتاری حفظ شدند؛ preflight واقعی در مجموعهٔ مستقل خود تست می‌شود |
| استانداردسازی | فاصله‌های انتهای خط در فایل‌های درگیر پاک و scope پیش‌فرض fixtureهای asyncio صریح شد. | `git diff --check`، compileall و مجموعهٔ کامل تست |

تغییر schema جدید یا تغییر شماره/محتوای مهاجرت‌های منتشرشده انجام نشد. قالب Fernet و envelope اطلاعات SSH ثابت ماند؛ این اصلاحات به بازرمزنگاری دادهٔ موجود نیاز ندارند.

## وابستگی‌های امنیتی

ممیزی اولیهٔ نسخه‌های نصب‌شده، ۳۳ رکورد advisory در ۶ بسته گزارش کرد؛ برخی شناسه‌ها در خروجی سرویس تکراری بودند. نسخه‌ها بر اساس metadata رسمی PyPI و سازگاری Python 3.10 به‌روز و سپس روی Python 3.12 اجرا شدند:

| بسته | قبل | بعد |
| --- | --- | --- |
| cryptography | 46.0.4 | 50.0.2 |
| paramiko | 3.5.1 | 5.1.0 |
| requests | 2.32.5 | 2.34.2 |
| WeasyPrint | 68.0 | 70.0 |
| pytest | 9.0.2 | 9.2.0 |
| FastAPI | 0.128.2 | 0.162.0 |
| Starlette | 0.50.0، انتقالی | 1.3.1، پین صریح سازگار با Python 3.10 |

ممیزی مجدد **همهٔ وابستگی‌های نصب‌شده در محیط برنامه** با `pip-audit` و سرویس PyPI: **No known vulnerabilities found**. این نتیجه به advisoryهای شناخته‌شده در زمان اجرا محدود است و اثبات امنیت مطلق نیست. نصب، TLS، امضاهای بسته‌ها و checksumهای منبع برای عبور از تست غیرفعال نشدند.

اسکن Bandit نیز انجام شد: ۰ مورد High، ۲۲ مورد Medium و ۱۶۵ مورد Low. موارد Medium بررسی‌شده عمدتاً ساخت SQL با نام جدول/ستون allowlist‌شده، فراخوانی SSH مدیریتی، bind شبکهٔ Agent و loader سفارشیِ مبتنی بر `yaml.SafeLoader` بودند. این هشدارها به‌صورت خودکار خاموش یا به‌عنوان آسیب‌پذیری رفع‌شده معرفی نشدند. خروجی کامل اسکن در `/workspace/.setup/evidence/sonar-bandit.json` محفوظ است.

## نتایج تست

محیط واقعی: Debian 13، Python 3.12.14، PostgreSQL 17.11. PostgreSQL با کاربر غیر root و پورت محلی 55432 در فضای کاری اجرا شد؛ دیتابیس عملیاتی کاربر در اختیار نبود و دست‌کاری نشد.

نتیجهٔ نهایی:

```text
364 passed, 8 warnings, 8 subtests passed in 30.89s
```

هیچ تستی در اجرای نهایی skip یا fail نشد. ۸ warning مربوط به APIهای deprecated کتابخانه‌های وب است؛ به شکست یا غیرفعال‌کردن assertion تبدیل نشدند. اجرای مستقیم این مجموعه بدون `SONAR_TEST_DB_DSN` سه آزمون PostgreSQL جدید را صریحاً skip می‌کند؛ اجرای نهایی این گزارش متغیر را داشت و هر سه اجرا شدند.

آزمون‌های واقعی جدید:

- ارتقای اسکیمای دارای داده و اجرای هم‌زمان دو پروسس مهاجرت؛ ۱۱ نسخه فقط یک بار ثبت و دادهٔ قبلی حفظ شد.
- تکرار مهاجرت‌ها بدون تغییر مجدد.
- ساخت بکاپ رمز‌شده با `pg_dump`، بازیابی موفق و تطبیق داده.
- شکست عمدی `pg_restore` و اثبات سالم‌ماندن داده پس از rollback.
- lifecycle واقعی FastAPI، ورود با کد یک‌بارمصرف و جلوگیری از استفادهٔ دوباره.
- ویژگی‌های Secure و HttpOnly کوکی، رد درخواست نوشتن فاقد CSRF و خروج/ابطال session.
- بررسی مجموعه‌ای از APIهای داشبورد، منابع، اشتراک‌ها، گزارش‌ها، اعلان‌ها، تیم، تنظیمات، سرویس‌ها و عملیات سازمانی روی PostgreSQL واقعی.
- جلوگیری از خواندن workspace و سرور کاربر دیگر و حذف رمز/توکن از خروجی جزئیات سرور.
- تبادل initData امضاشدهٔ آزمایشی به session مینی‌اپ، بدون تماس با تلگرام.
- تولید فایل PDF واقعی با WeasyPrint/Pango.
- بارگذاری کلید RSA رمز‌شدهٔ واقعی با Paramiko به‌روز.
- درخواست واقعی WebSocket برای کنترل Origin و درخواست HTTP برای الزام تأیید re-enrollment.

بررسی‌های تکمیلی: `pip check`، compilation پایتون، نحو Bash، نحو تمام JavaScriptهای static، preflight نصب‌کننده، manifest منبع و ساخت ZIP قطعی. صفحات وب و static asset از API در حال اجرا نیز با HTTP محلی بررسی شدند؛ این کار جای آزمون بصری مرورگر را نمی‌گیرد.

## وضعیت محیط توسعه و تنظیمات ذخیره‌شده

محیط مجازی: `/workspace/.venvs/radarsonarplus`.

اسکریپت‌های تست‌شده خارج از سورس:

```bash
bash /workspace/.setup/install_environment.sh
bash /workspace/.setup/start_environment.sh
```

نصب و startup به‌صورت تکراری اجرا شدند. وابستگی‌ها و فایل‌های PostgreSQL قابل نگهداری در snapshot هستند؛ پروسس‌های PostgreSQL و Uvicorn باید در task بعدی دوباره راه‌اندازی شوند. `install_script` و `start_skill` کامل در draft محیط ذخیره شدند. ذخیرهٔ draft به معنی انتشار یا تأیید بازیابی در task تازه نیست؛ برای فعال‌کردن snapshot، تنظیمات محیط باید بازبینی و ذخیره و سپس Publish شوند.

اجرای تست قابل تکرار:

```bash
cd /workspace/radarsonarplus
export PATH=/workspace/.venvs/radarsonarplus/bin:/workspace/.setup/pgroot/usr/lib/postgresql/17/bin:$PATH
export LD_LIBRARY_PATH=/workspace/.setup/pgroot/usr/lib/x86_64-linux-gnu${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}
SONAR_TEST_DB_DSN='host=127.0.0.1 port=55432 user=agent dbname=postgres' python -m pytest -q --disable-warnings
python -m pip check
bash install.sh --check
python scripts/verify_manifest.py
```

## محدودیت‌ها و کارهای لازم پیش از استقرار عملیاتی

- این ماشین دسترسی root و systemd عملیاتی ندارد. نصب تازه و آپدیت کامل روی میزبان Debian/Ubuntu دارای systemd در این نوبت اجرا نشدند؛ تست‌های موجود نصب‌کننده، preflight و مسیرهای واقعی دیتابیس اجرا شدند.
- توکن معتبر تلگرام، دامنهٔ عمومی و نود آزمایشی SSH/WSS ارائه نشده‌اند. ارسال پیام واقعی، polling ربات، نصب Agent روی VPS، firewall، TLS عمومی و رفتار Mini App داخل کلاینت واقعی Telegram تأیید نشده‌اند.
- بدون توکن واقعی، `/healthz` موفق و `/readyz` با `db=ok, auth=unconfigured` برابر 503 است. این وضعیت عمداً آمادگی عملیاتی اعلام نمی‌کند. توکن را در چت یا سورس نگذارید؛ از پیکربندی خصوصی و مستندشدهٔ برنامه استفاده کنید.
- آزمون بصری/تعامل کامل مرورگر و کلاینت تلفن همراه اجرا نشد؛ تست‌های JavaScript موجود، routing و API اجرا شدند.
- سرویس S3 واقعی پیکربندی نشده است؛ تست‌های واحد مسیر اختیاری آن اجرا شدند، اما upload/download واقعی تأیید نشده است.
- اجرای واقعی Python 3.10 و 3.11 در این ماشین انجام نشد؛ CI موجود همچنان matrix آن‌ها را دارد. بررسی metadata جای اجرای آن‌ها را نمی‌گیرد.
- حفظ داده در سناریوهای موفق و شکست آزموده شد؛ پیش از ارتقای دیتابیس واقعی همچنان باید backup دیتابیس و **کلید رمزنگاری متناظر** با هم نگهداری و روی staging بازیابی شوند. بکاپ دیتابیس به‌تنهایی جای `secret.key` را نمی‌گیرد.

شواهد اجرای نهایی، ممیزی وابستگی و اسکن منبع در `/workspace/.setup/evidence/` قرار دارند. تغییرات این گزارش محلی‌اند؛ انتشار در GitHub یا استقرار عملیاتی انجام نشده است.
