## معرفی

**SONAR RADAR PRO** یک سامانه مدیریتی برای کنترل سرورها، Agentهای راه دور، کانفیگ‌ها و سرویس‌های مانیتورشده است. هدف پروژه این است که عملیات روزمره از یک فضای کاری واحد قابل مشاهده و مدیریت باشد؛ درحالی‌که وضعیت واقعی اتصال، سلامت سرویس و نتیجه عملیات از داده‌های ثبت‌شده گزارش شود، نه از پیام‌های موفقیت ظاهری.

ربات تلگرام، پنل وب و Mini App اجزای مختلف همین سامانه‌اند. عملیات پشتیبانی‌شده از مسیرهای مشترک برنامه و پایگاه داده استفاده می‌کنند؛ دسترسی هر قابلیت نیز بر اساس سطح مجوز و API مربوط تعیین می‌شود.

> **وضعیت استقرار:** این مخزن در وضعیت Release Candidate قرار دارد. پیش از استفاده عملیاتی، نصب، بازیابی بکاپ و ارتباط واقعی SSH/WSS/TLS را در محیط آزمایشی بررسی کنید.

## نمای کلی معماری

```text
                    ┌──────────────────────┐
                    │   Telegram Bot       │
                    └──────────┬───────────┘
                               │
┌──────────────────────┐       │       ┌──────────────────────┐
│ Web Panel / Mini App │───────┼───────│ Shared Application   │
└──────────────────────┘       │       │ Logic & API          │
                               │       └──────────┬───────────┘
                               │                  │
                               │        ┌─────────▼──────────┐
                               └────────│ PostgreSQL / State │
                                        └────────────────────┘

    Central SSH route ── first choice ──► Destination server
              │
              └── approved Agent relay ─► Destination server
```

- **مسیر اصلی:** اتصال از کنترل‌کننده مرکزی بررسی می‌شود.
- **مسیر جایگزین:** فقط Agentهای مجاز و سالم برای تلاش مجدد انتخاب می‌شوند.
- **اعتماد SSH:** اثرانگشت میزبان باید از منبع مستقل تأیید شود؛ خطای `HOST_KEY_UNKNOWN` یا `HOST_KEY_CHANGED` مجوز اعتماد خودکار نیست.
- **اعتماد Agent:** دسترسی شبکه یا بازبودن پورت به‌تنهایی سلامت Agent را ثابت نمی‌کند؛ وضعیت TLS، توکن و heartbeat نیز باید معتبر باشند.
- **بالانسر:** انتخاب مسیر باید اولویت، سلامت، بار و پایداری مسیر را در نظر بگیرد؛ تغییر مکرر مسیر بدون دلیل مطلوب نیست.

## پیش‌نیازها

- Ubuntu 22.04/24.04 یا Debian سازگار با systemd
- Python و وابستگی‌های تعریف‌شده در فایل‌های requirements پروژه
- PostgreSQL
- دسترسی مدیریتی `sudo` برای نصب بسته‌های سیستم و مدیریت سرویس‌ها
- توکن ربات تلگرام و شناسه عددی مدیر
- دامنه و HTTPS برای پنل عمومی و Telegram Mini App
- دسترسی SSH و یک مقصد آزمایشی برای ارزیابی Agentها
- برای حساب SSH غیر از `root` (از جمله `ubuntu`)، دسترسی `sudo -n` الزامی است؛ اجرای خودکار منتظر ورود تعاملی رمز sudo نمی‌ماند.

بررسی مجوز sudo روی سرور مقصد:

```bash
sudo -n true
sudo -n id -u
```

دستور دوم باید `0` برگرداند. اگر پیام `SUDO_REQUIRED` دریافت شد، مجوز sudo حساب را در خود سرور مقصد تنظیم کنید؛ ربات رمز sudo را در فرمان‌ها قرار نمی‌دهد.

## نصب

برای دریافت مستقیم اسکریپت نصب از مخزن رسمی پروژه:

```bash
wget https://raw.githubusercontent.com/Amirtn9/radarsonarplus/main/install.sh
chmod +x install.sh
chmod 700 install.sh
sudo ./install.sh --check
sudo ./install.sh
```

اگر مخزن را به‌صورت کامل دریافت می‌کنید، ابتدا فایل‌های نصب را بررسی کنید:

```bash
sudo apt-get update
sudo apt-get install -y git ca-certificates

git clone https://github.com/Amirtn9/radarsonarplus.git
cd radarsonarplus
bash install.sh --check
sudo bash install.sh
```

در منوی نصب، گزینه نصب کامل را انتخاب و مراحل راهنما را تکمیل کنید. برای اجرای دوباره منو:

```bash
sudo bash install.sh
```

> دستور `git clone` معمولاً بهتر است با کاربر استقرار اجرا شود تا فایل‌های مخزن بی‌دلیل root-owned نشوند. از `sudo` برای نصب سیستم، تغییر سرویس‌ها و عملیات مدیریتی استفاده کنید. اگر پوشه مقصد عمداً تحت مالکیت root است، مجوزها را پیش از ویرایش بررسی کنید.

### پیکربندی اولیه

1. توکن ربات و شناسه عددی مدیر را فقط در مرحله پیکربندی امن وارد کنید.
2. پایگاه داده را راه‌اندازی و اتصال آن را بررسی کنید.
3. پنل وب را پشت HTTPS و reverse proxy معتبر منتشر کنید.
4. ابتدا یک سرور آزمایشی اضافه کنید و اثرانگشت SSH را از کنسول یا پنل ارائه‌دهنده همان سرور بررسی کنید.
5. Agent را نصب کنید و سلامت TLS/WSS و heartbeat را بررسی کنید.
6. مسیر مرکزی و سپس failover به Agent را در یک آزمون کنترل‌شده ارزیابی کنید.
7. پیش از فعال‌سازی روی زیرساخت اصلی، بکاپ و روش بازیابی را آزمایش کنید.

## دستورات نگهداری

بررسی سلامت نصب:

```bash
sudo bash install.sh --doctor
sudo bash install.sh --status
```

ساخت بسته پشتیبانی:

```bash
sudo bash install.sh --support
```

مشاهده لاگ خطاها:

```bash
sudo bash install.sh --logs errors --lines 200
```

اجرای آزمون‌های پروژه پس از نصب وابستگی‌های توسعه:

```bash
python3 -m compileall -q .
bash -n install.sh
node --check pro_web/static/app.js
python3 -m pytest -q
```

اگر وابستگی‌های تست در محیط نصب نشده باشند، نتیجه را ناقص یا مسدودشده در نظر بگیرید؛ اجرا نشدن آزمون به معنی موفقیت آن نیست.

## امنیت

- توکن ربات، رمزهای SSH، کلیدهای خصوصی، `secret.key` و فایل‌های محیطی نباید به Git یا گزارش پشتیبانی وارد شوند.
- از HTTPS برای پنل و WSS/TLS برای ارتباط Agent استفاده کنید.
- اثرانگشت SSH را مستقل از همان اتصال بررسی کنید و سیاست‌های بررسی کلید SSH/TLS را غیرفعال نکنید.
- دسترسی عملیات حساس را به مالک یا نقش مجاز محدود کنید.
- از محدودکردن پورت‌های ورودی، فایروال و اصل حداقل دسترسی استفاده کنید.
- قبل از ارتقا یا تعمیر، از دیتابیس، تنظیمات محرمانه و `known_hosts` نسخه پشتیبان تهیه کنید.
- بسته پشتیبانی ممکن است شامل آدرس سرورها، نام سرویس‌ها یا داده عملیاتی باشد؛ پیش از ارسال، محتویات آن را بازبینی کنید.

## لاگ‌ها و بسته پشتیبانی

از ابزار عیب‌یابی مدیر یا دستور `sudo bash install.sh --support` بسته پشتیبانی تهیه کنید. در صورت نیاز به تحلیل چندمسیره، وضعیت کنترل‌کننده مرکزی، Agentها، سرویس‌ها و لاگ‌های در دسترس باید در بازه زمانی مشخص جمع‌آوری شوند.

کامل‌بودن لاگ‌ها به retention سیستم، تنظیمات journald، مجوزهای سرویس و دسترسی هر سرور بستگی دارد. اگر یک Agent آفلاین یا فاقد مجوز باشد، لاگ آن سرور ممکن است در بسته موجود نباشد؛ این مورد باید به‌عنوان نقص جمع‌آوری گزارش شود، نه اینکه خروجی کامل فرض شود.

## عیب‌یابی سریع

**`HOST_KEY_UNKNOWN`** — کلید میزبان هنوز تأیید نشده است. اثرانگشت را از کنسول مستقل سرور بررسی و از مسیر تأیید رسمی ثبت کنید.

**`VENV_CREATE_FAILED`** — نسخه Python، بسته `python3-venv` و امکان ایجاد محیط مجازی باید روی مقصد بررسی شوند. نصب سیستم از طریق `sudo` انجام می‌شود.

**Agent آفلاین است** — وضعیت سرویس، پورت ثبت‌شده، فایروال، TLS، توکن و heartbeat را بررسی کنید. SSH Online به‌تنهایی به معنی Agent سالم نیست.

**پنل در دسترس نیست** — وضعیت سرویس وب، reverse proxy، گواهی HTTPS، اتصال PostgreSQL و خروجی `--doctor` را بررسی کنید.

## محدوده تضمین

این نرم‌افزار ابزار مدیریت زیرساخت است و وضعیت واقعی آن به پیکربندی مقصد، دسترسی شبکه، اعتبار گواهی‌ها و سرویس‌های وابسته بستگی دارد. وجود قابلیت در رابط کاربری به‌تنهایی تضمین اجرای موفق آن روی هر سرور نیست. پیش از استفاده عملیاتی، مسیرهای SSH، Agent، TLS/WSS، دیتابیس، بکاپ و بازیابی را روی محیطی که کنترل می‌کنید آزمایش کنید.

## مجوز و مشارکت

پیش از بازنشر یا توزیع، وضعیت مجوز انتشار را از مالک مخزن مشخص کنید و `SECURITY.md` را برای گزارش آسیب‌پذیری‌ها بخوانید. برای گزارش مشکل، نسخه سیستم‌عامل، پیام خطای دقیق، زمان رخداد و خروجی پاک‌سازی‌شده عیب‌یابی را ارائه دهید؛ اطلاعات محرمانه و کلیدها را ارسال نکنید.
